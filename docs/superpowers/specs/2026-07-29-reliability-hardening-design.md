# Reliability Hardening Design

**Status:** Architecture approved; awaiting written-spec review  
**Date:** 2026-07-29  
**Target:** Onboard at revision `06edb074bff69a5211efc35db9a4d6b03cb8f5a0`

## Objective

Resolve the complete review backlog without adding product functionality or
changing the compact Go, WebSocket, Canvas, and plain-JavaScript architecture.
The happy path remains: start the binary, open Board, open Viewer, draw.

This work covers deterministic correctness defects, the six validated security
findings, client input/rendering problems, release reproducibility, maintenance
drift, and the two browser-bound hardening candidates that can be removed with
strict protocol bounds.

## Non-goals

- No accounts, cloud service, database, or persistent board storage.
- No new drawing tools, routes, frameworks, build systems, or runtime
  dependencies.
- No visual redesign of Board or Viewer.
- No public-Internet deployment support.
- No compatibility layer for malformed or out-of-policy relay events.

## Global Invariants

1. A WebSocket is usable only after the relay snapshot has been consumed and a
   `system:relay-ready` marker has arrived.
2. Locally queued Board events survive initial connection and reconnect without
   disappearing from the Board or being duplicated in the relay.
3. Stroke IDs are unique across Board reloads, restores, and direct relay
   clients.
4. Retained state, identifiers, expiry times, and connection lifetimes have
   explicit limits shared by Go and browser validation.
5. Only a client holding the current process's presenter capability may acquire
   the Board role.
6. A silent or half-open presenter releases its role within a bounded interval.
7. Viewer remains content-only and the normal user workflow needs no account or
   cloud coordination.

## Fixed Protocol And Runtime Limits

The implementation will use explicit constants and matching regression tests:

| Limit | Value |
| --- | ---: |
| Event ID | 128 UTF-8 bytes |
| Stroke ID | 128 UTF-8 bytes |
| Board ID | 64 UTF-8 bytes |
| Color string | 64 UTF-8 bytes |
| Strokes in current state | 4,096 |
| Points in one stroke | 8,192 |
| Points in current state | 65,536 |
| Serialized current board state | 7,500,000 UTF-8 bytes |
| Ephemeral lifetime after event timestamp | 60 seconds |
| Background data URL | existing 6,000,000-character limit, JPEG base64 only |
| Recent event IDs | existing 8,192 entries, now byte-bounded by ID length |
| WebSocket connections | 128 process-wide, 64 per source IP |
| HTTP header read timeout | 5 seconds |
| HTTP idle timeout | 60 seconds |
| HTTP maximum header size | 16 KiB |
| WebSocket heartbeat | ping every 15 seconds, 5-second response timeout |
| Relay-ready timeout | 5 seconds before reconnect |

These values are intentionally generous for the local teaching workflow while
putting a finite upper bound on every retained or repeatedly processed input.
`board:clear` and `board:restore` reset the relevant state counters.

## Lot 1: Protocol, State, And Synchronization

### Canonical state and snapshots

`internal/hub` will stop rebuilding and storing a complete `board:restore`
event after every delta. The Hub will retain canonical `boardSnapshot` state
and only the metadata needed to identify the most recent accepted event.
`Snapshot` and new subscriptions will materialize one restore event on demand.
Live subscribers continue receiving validated deltas.

The snapshot will maintain stroke, active-stroke, total-point, per-stroke byte,
and aggregate-state byte accounting. A restore calculates its size once; delta
events update the counters from only the changed stroke or point. `Apply`
rejects a start, point, or restore that exceeds the fixed limits or introduces
a duplicate stroke ID. The shared browser reducer enforces the same state
limits so a normal Board cannot apply an event locally that the Hub will reject.

### Identifier and payload validation

Go parsing and `web/core/protocol.js` will enforce matching identifier and color
lengths. Backgrounds will accept only the JPEG base64 data URLs produced by the
existing Board image normalization path. Ephemeral start events must expire no
later than 60 seconds after their event timestamp; restored ephemeral strokes
may already be expired but cannot schedule an expiry more than 60 seconds after
the restore event.

Stroke IDs generated by `web/board` will use the existing random event-session
identifier plus a controller-local monotonic counter:

```text
stroke_<session-id>_<six-digit-counter>
```

The reducer and Hub still reject duplicates so uniqueness is not trusted solely
to client generation.

### Ready handshake and queued-event rebase

After sending zero or one snapshot events, the server sends
`system:relay-ready`. The transport consumes this marker internally. Before it
arrives, incoming snapshot events are delivered to the controller, but outgoing
events stay queued and status remains connecting/reconnecting.

When a Board receives `board:restore` while it has queued local events, it:

1. applies the authoritative restore;
2. reapplies its queued events in original order to local state;
3. waits for `system:relay-ready`;
4. flushes the same event IDs to the relay.

Echoes are ignored by normal event-ID deduplication. An empty relay snapshot
does not replace local state. Initial open/error paths use the same reconnect
scheduler as runtime disconnects, and a socket that opens but never becomes
ready is closed and retried.

## Lot 2: Presenter Authorization And Network Liveness

### Presenter capability

The Go process generates a cryptographically random 256-bit base64url presenter
capability at startup. It is printed only in trusted startup Board URLs, using a
URL fragment so it is not sent in HTTP requests or referrers:

```text
http://host:port/board#presenter=<capability>
```

Home and Board JavaScript retain a capability received through the fragment
in local storage for that browser. Home propagates a stored capability only to
the Board link. Viewer links and `/api/share` never contain it. The Board sends
the capability only as the `presenter` WebSocket query parameter.

The server compares it in constant time before acquiring the presenter role.
An invalid or missing value receives `system:presenter-unauthorized` and a
policy close. Existing `system:presenter-conflict` remains reserved for a valid
second presenter. Restarting the process invalidates old capabilities.

### Ownership and heartbeat

Presenter ownership changes from a process-wide boolean to an opaque
connection-owner ID. Release succeeds only for the current owner, preventing a
stale handler from releasing a newer presenter.

The single writer loop handles event writes and heartbeat pings serially. A
failed ping closes the socket; the reader exits and the matching owner is
released. This bounds silent presenter loss to approximately 20 seconds without
requiring browser-generated application messages.

### HTTP and WebSocket admission

`http.Server` receives header/idle limits and `MaxHeaderBytes`. A small
in-process connection gate protects `/ws/relay` before upgrade, with global and
per-source-IP counters released on every exit path. Excess connections receive
HTTP 503. Viewer behavior is otherwise unchanged.

## Lot 3: Board And Viewer Correctness

### Pointer ownership

Only the first active pointer owns a stroke or explicit pointer operation.
Additional pointer-down events are ignored until the owner ends or is canceled;
they do not overwrite the active stroke. `lostpointercapture`, cancel, leave,
and close share one idempotent cleanup path so palm contact cannot abandon a
stroke or leave the explicit pointer visible.

### Device-pixel-ratio rendering

Canvas backing dimensions remain DPR-scaled. Board and Viewer calculate the
effective ratio from backing width versus CSS width and pass it to the shared
renderer. Stroke widths, chalk particles/dust, eraser widths, and pointer size
are multiplied by that ratio while normalized coordinates continue using the
physical viewport. This preserves the same apparent CSS-pixel width at DPR 1,
2, and 3 without changing stored stroke data.

### Collapsed toolbar accessibility

When compact controls collapse, the presenter toolbar becomes `inert` and
`aria-hidden="true"`; expansion removes both. If focus is inside the toolbar
when it collapses, focus returns to the compact toggle. Desktop behavior and
the visual transition remain unchanged.

## Lot 4: Release, Packaging, Toolchains, And Documentation

### Reproducible and non-destructive releases

`scripts/build-release.sh` accepts `DIST_DIR`, defaulting to `dist`, and builds
with `-trimpath -ldflags="-s -w"`. The shell test always uses a temporary output
directory and never removes pre-existing release files.

Release output includes `LICENSE` and a `THIRD_PARTY_NOTICES.md` containing the
ISC notice for `github.com/coder/websocket`. Checksums cover binaries and notice
files. Cross-build tests verify identical output hashes from two checkout paths
when source revision and toolchain match.

### Embedded assets

`web/assets.go` replaces the broad `//go:embed *` pattern with explicit HTML,
CSS, manifest, icon, and production-JavaScript patterns. Go source and
`*.test.mjs` files must not appear in the embedded filesystem or release binary.

### Tooling and installer

- Pin Go `1.26.5`, the current supported patch release with security fixes.
- Pin Node `24.18.0` LTS and npm `11.16.0`, matching the currently published
  Node bundle. A newer announced Node security release is not pinned until it
  is actually available from the official `latest-v24.x` archive.
- Add `govulncheck ./...` to the documented security/release verification when
  the tool is installed; absence is reported explicitly rather than silently
  skipped.
- The Go installer downloads the official archive checksum, verifies it before
  touching `/usr/local/go`, validates the staged `go` binary, and uses a backup
  plus rollback around the final directory swap.

### LAN URL selection and documentation

LAN candidates are deterministic: physical Ethernet/Wi-Fi-style interfaces are
ranked before unknown interfaces; tunnel/VPN/container/VM bridge names are
deprioritized or excluded from the preferred set. Private IPv4 addresses rank
before other usable IPv4 addresses. Existing result limits remain two preferred
addresses or one virtual fallback.

Documentation will be updated to match actual behavior for snapshot-on-join,
Viewer fullscreen feedback, in-memory persistence, presenter capability,
heartbeat recovery, release artifacts, and the final verification sequence.

## Error Handling

- Invalid protocol input is rejected before state mutation or broadcast.
- A state-limit rejection leaves both browser and Hub state unchanged.
- Unauthorized and conflicting presenters have distinct system events and UI
  statuses.
- Ready timeout, socket failure, and heartbeat failure all enter the same
  bounded reconnect path.
- Connection-gate counters and presenter ownership use idempotent deferred
  cleanup.
- Release and installer scripts preserve existing artifacts/installations until
  the replacement has been built, verified, and staged successfully.

## Test Strategy

Every behavior change follows a red-green-refactor cycle.

### JavaScript unit tests

- session-qualified stroke IDs and duplicate rejection;
- protocol string, state, background, and expiry limits;
- snapshot rebase followed by ready-only flush;
- initial failure retry and open-without-ready timeout;
- second-pointer/palm and lost-capture behavior;
- DPR-stable marker, chalk, eraser, and pointer dimensions;
- toolbar `inert`, `aria-hidden`, and focus return;
- presenter fragment parsing, storage, and WS URL construction.

### Go unit and integration tests

- snapshot materialization only on `Snapshot`/subscribe and bounded state;
- duplicate IDs and oversized identifiers/restores are rejected;
- ready marker ordering for empty and populated snapshots;
- presenter capability, owner-safe release, conflict, and heartbeat cleanup;
- global/per-IP admission cleanup;
- HTTP server timeout configuration;
- deterministic LAN candidate ranking;
- embedded filesystem excludes source and tests.

### Shell and release tests

- temporary `DIST_DIR` preserves seeded `dist` artifacts;
- `-trimpath` reproducibility from separate checkout paths;
- notices and checksums are complete;
- installer refuses bad checksums and preserves the old installation on staged
  failure.

### Final verification

Run JavaScript tests, Go unit tests, Go race tests, `go vet`, module verification,
npm audit, shell tests, release cross-builds/checksums, the local browser smoke
script, `git diff --check`, and a clean status review. Browser smoke must cover
Board/Viewer ready ordering, reconnect, a second presenter, phone-size pointer
input, DPR rendering, and Viewer-only controls.

## Rollout And Compatibility

The protocol changes are intentionally same-version: a refreshed Board and
Viewer are served by the same local binary. Old open tabs may fail the ready or
presenter-capability handshake and must be refreshed after upgrading. No board
data migration exists because state remains process-memory-only and restart
already clears it.
